[[send]]
= Send and incremental parsing

`parse`, the subject of xref:3_02_parse.adoc#parsing[the parsing chapter],
takes all of its input in one statement, and ends the input after the last
item. A program can also make a parser, send it input a piece at a time, and
end the input when there is no more. This chapter covers parser objects and
`send`, ending the input, `send_tree`, streams and files, writing output
through a parser with `+<<+`, trimming what a send sends, and using a parser's
input from a token action.

== Parser objects

`new parser<T>()` makes a parser that builds a tree of type `T`. `send` sends
it input. `+finish()+` ends the input, and returns the tree:

[source,colm]
----
P: parser<program> = new parser<program>()
send P "width = 80;"
send P " height = 24;"
Program: program = P->finish()
----

`new P: parser<program>()` makes the parser and declares `P` in one
statement. A parser variable is nil until it is given a parser made with
`new`. Make the parser before sending to it. Sending to a nil parser stops
the program, as xref:8_04_error_handling.adoc#run-time-errors[the error
handling chapter] says. So do `+finish()+`, `+P->tree+`, `+P->error+` and
`+P->gets()+` on a nil parser.

`+finish()+` returns nil when the input doesn't form a tree of the type.
After the input has ended, `+P->tree+` is the tree, or nil, and `+P->error+`
is nil, or a message that says where the parse failed.

A parser is a reference. Assigning it to another variable, or passing it to a
function, doesn't copy it. Sends through either go to the same parser, as the
function `feed` in the next example shows.

`accum<T>` is another name for `parser<T>`, and `+P->eof()+` another name for
`+P->finish()+`.

A parser can also be given a context, for a grammar defined inside a
`context` block: `+new parser<ctx::program>( new ctx() )+`.
xref:3_04_undo.adoc#context[The context chapter] covers contexts.

== Sending input piece by piece

`send P` is followed by the items to send. They are the items of a `parse`:
strings, `str` and `int` values, trees, which are sent as their text, and
streams, such as `stdin`. Any other value, such as a list or a struct, is an
error. Items other than strings go in square brackets, as in
`+send P [Name " = " Value]+`. A string can stand on its own, and can hold
items of its own in square brackets: `+send P "[Name] = [Value];"+`.

The parser runs as far as each send lets it. Text at the end of a send that
more text could make into a longer token, such as a word, waits for the next
send. So a token can be split across two sends. A reduction waits for the
token after it, since the parser needs that token to choose what to do.

of the input is the token after it.

Backing up, which xref:3_02_parse.adoc#parsing[the parsing chapter] describes,
can go back into the text of earlier sends.

`send` is an expression, whose value is the parser:
`+Q: parser<program> = send P "a = 1;"+` sends the text, and makes `Q` the
same parser as `P`.

After a parse error, later sends do nothing.

== Ending the input

`eos` after the items of a send ends the input after them, as in
`+send P "depth = 3;" eos+`. A `.` can take its place:
`+send P "depth = 3;" .+` is the same. `+P->finish()+` ends the input too,
and returns the tree.

End the input once: with `eos` on the last send, or with `+finish()+`, not
both. Read `+P->tree+` only after the input has ended. Before then, the
parser has no finished tree to give.

A `parse` that fails sets the global `error`, but `send` and `+finish()+`
don't. Read `+P->error+` instead.

== `send_tree` and `parse_tree`

`send` sends a tree as its text, which the parser scans again. The tokens it
finds can be of other types than the tree's. `send_tree` sends a tree as it
is, with its type, as one piece of input. The parser must be able to take a
tree of that type where it comes, or the parse fails. Strings sent with
`send_tree` are still scanned. `parse_tree` is `parse`, with its items sent
as `send_tree` sends them.

== Streams

`stdin`, `stdout` and `stderr` are streams. `open( Name, Mode )` opens a file,
and returns a stream. With the mode `"r"`, the stream reads the file. With
`"w"`, it writes the file, which `open` empties first, and with `"a"` it
writes at the file's end. Any other mode stops the program with an error.
When the file can't be opened, `open` returns nil. Always check its result
before using it. Sending to a nil stream stops the program, as
xref:8_04_error_handling.adoc#run-time-errors[the error handling chapter]
says. So do sending one to a parser or parsing from one, pushing it with
`+input->push_stream+`, calling its functions, and reading its `+tree+`.
`+S->close()+` closes a stream.

`send S "text"` writes the text to the stream `S`. `print` sends to
`stdout`: `print "text"` is `send stdout "text"`. `+prints( S, A, B )+`
writes `A` and `B` to `S`, as `+print( A, B )+` writes them to `stdout`. A
send to a stream can end with `eos`, which does nothing there.

A stream sent to a parser, as in `+send P [File]+`, is read in full, and text
sent after it comes after the stream's text. A stream sent to a stream is an
error.

`new stream()` makes a stream that keeps what is sent to it, and `+S->tree+`
is the text it holds.

== Writing output through a parser: `+<<+` and `+<-+`

`+<<+` followed by items sends them to the variable named `+_+`:
`+<< "text"+` is `+send _ "text"+`. `+<-+` is the same as `+<<+`. `+_+` has to
be a variable that can be used where the `+<<+` is, such as a global, as in
the next example, or a local. It can be a parser or a stream.

A string with no closing quote runs to the end of the line, and takes the
line break with it. As in a `send`, the items can go on over several lines,
so one `+<<+` can write several lines of output, one string to each.

Output sent to a parser, rather than to a stream, is checked: it has to parse
as the parser's type. The program then has the output as a tree, which it can
search, change and print. The programs that write ragel's output in its host
languages, `src/cgil/rlhc-*.lm`, work this way. Each sends its output to a
parser for the host language, and writes the tree out only when the parse
succeeds. Those for C, Go and Zig send it with `+<<+`.

== Trimming

A tree holds the ignored text next to it, as xref:3_01_lex.adoc#lexing[the
lexing chapter] explains, and sending a tree sends that text too. A parser's
input can trim it off instead. `+P->gets()+` returns the input, and
`+auto_trim( true )+` on the input makes the trees sent to the parser lose
the ignored text around them:

[source,colm]
----
Input: _input = P->gets()
Input->auto_trim( true )
----

In the items of a send, `+^X+` sends `X` without the ignored text around it,
and `@X` sends it with that text, whatever `auto_trim` says. The same goes
for a `print` followed by a string or square brackets. In `+print( ... )+`,
with parentheses, `@X` is the same as `X`.

== The parser's input in token actions

In a token action, `input` is the input of the parser that the token is for.
xref:3_01_lex.adoc#lexing[The lexing chapter] covers `+input->pull+`,
`+input->push+`, `+input->push_ignore+` and `make_token`. Two more things can
be done with it there:

* `+input->push_stream( S )+` puts the stream `S` at the front of the input.
  The scanner reads all of `S`, and then goes on with the text after it.
* `+parse_stop T( input )[]+` parses a `T` from the input, from the start of
  the text the token matched, and stops as soon as it has one. The parser the
  token is for goes on after the `T`.

token `hash` matches a `+#+`. Its action parses an `include_line` from the
input with `parse_stop`. The include line's tokens are in a region of their
own, so the file name is a single token there. When the parse succeeds, the
action opens the file, and pushes it onto the input. The action pushes no
token, so the parser never gets the `+#+`, and reads the file's assignments
in place of the line. When the parse fails, `parse_stop` leaves the `+#+` in
the input. The action pulls it, so that the scanner doesn't match it again
without end, and the rest of the line is scanned as usual.

Here the input is `stdin`, given to `parse` whole. Give `parse_stop` from
`input` its input whole like this, and don't use it on text that is sent to a
parser a piece at a time.
