[[lexing]]
= Lexical analysis

A colm program that parses text has two parts that work together. The
scanner reads the input and breaks it into tokens: names, numbers,
punctuation. The parser builds a tree from the tokens, following the grammar.
It asks the scanner for the next token each time it needs one.

This chapter covers the scanner: how to define tokens, how to give a pattern
a name, how the scanner picks a token when several patterns match, how to scan
different parts of the input with different patterns, and how to run code
when a token is read. The grammar itself, written with `def`, is the subject
of xref:3_02_parse.adoc#parsing[the parsing chapter].

== Tokens, ignores and literals

Tokens are defined in a `lex` block, with three kinds of definition. A
pattern is written between two slashes.

* `token NAME /PATTERN/` defines a token called `NAME`.
* `ignore /PATTERN/` defines text the scanner reads but doesn't pass to the
  parser as a token, such as whitespace and comments. A `def` never names it.
* `literal` defines tokens for fixed text. Each is written as a backtick
  followed by the text, which runs up to the next space, tab, line break
  or `]`: `+literal `( `)+` defines the tokens `(` and `)`.

A `def` uses a token by its name, and a literal by its backtick form. Every
literal that a `def` uses must be defined by a `literal` statement. Colm
reports an `unknown type` error for one that isn't.

== Named regular languages

A pattern is a regular expression. The table shows the parts of a pattern
used most. `x` and `y` stand for any pattern.

[cols="2,3"]
|===
| Pattern | Matches

| `'abc'` or `"abc"`
| the text `abc`

| `+'abc'i+`
| `abc` in upper or lower case, `aBC` for example

| `'\n'`, `'\t'`
| a newline, a tab

| `[abc]`, `[a-z]`
| one of the characters listed, or one in the range

| `[^abc]`
| any one character not listed

| `'a' .. 'z'`
| any one character from `a` to `z`

| `^'a'`
| any one character but `a`

| `any`
| any one character

| `x y` or `x . y`
| `x` followed by `y`

| `x \| y`
| `x` or `y`

| `x & y`
| text that matches both `x` and `y`

| `x - y`
| text that matches `x` but not `y`

| `x*`, `x+`, `x?`
| `x` zero or more times, one or more times, zero times or once

| `x{3}`, `x{2,}`, `x{,2}`, `x{2,3}`
| `x` exactly three times, two or more times, up to two times, two or three
  times

| `( x )`
| `x`, grouped
|===

A few less common operators are left out of the table above. Like the rest
of colm's patterns, they come from ragel. This table lists them, and the ways
to write a character by its code. With the two tables, every operator a
pattern can have is covered.

[cols="2,3"]
|===
| Pattern | Matches

| `97`, `0x61`
| the character with that code, here `a`. A code is decimal, or hex after a
  lowercase `0x`, and runs from 0 to 255.

| `97 .. 99`, `'a' .. 99`
| any one character in the range, here `a` to `c`. Either end can be a code
  or a quoted character. Inside `+[...]+`, digits are characters: `[97]` is
  `9` or `7`.

| `+x -- y+`
| text that matches `x` and doesn't contain a match of `y` anywhere. See the
  next section.

| `x :> y`
| `x` followed by `y`, where `x` stops at the first character that can start
  `y`. See the next section.

| `x :>> y`
| `x` followed by `y`, where the match ends at the first complete `y`. See
  the next section.

| `x <: y`
| `x` followed by `y`, where `x` takes every character it can. `y` can start
  only on a character `x` can't take. See the next section.

| `+x**+`
| like `+x*+`, but each round of `x` goes on as long as it can. See the next
  section.
|===

`:>`, `:>>` and `<:` bind like concatenation, from left to right, so in
`+'/*' any* :>> '*/'+` the left side is `+'/*' any*+`. `+--+` binds like `-`.

Colm has names for common sets of characters:

[cols="1,3"]
|===
| Name | Characters

| `alpha` | `A` to `Z` and `a` to `z`
| `digit` | `0` to `9`
| `alnum` | `alpha` and `digit`
| `lower`, `upper` | `a` to `z`, `A` to `Z`
| `xdigit` | `0` to `9`, `a` to `f` and `A` to `F`
| `space` | space, tab, newline, vertical tab, form feed and carriage return
| `punct` | the printable characters that are not letters, digits or space
| `graph` | the printable characters but space, `!` to `~`
| `print` | `graph` and space
| `cntrl` | the control characters, 0 to 31 and 127
| `ascii` | characters 0 to 127
|===

Text in a pattern has to be quoted. A bare word is a name. `rl` gives a
pattern a name, so that other patterns can use it:

[source,colm]
----
rl letter /alpha | '_'/
----

A name has to be defined before a pattern uses it. A token's name can be used
in a pattern as well, like a name defined with `rl`.

The difference between `rl` and `token` is that an `rl` is not a token. The
scanner never matches it on its own, and a `def` can't use it. It is only a
part of other patterns. An `rl` can be defined inside a `lex` block or outside
one, and in both cases the patterns that follow it can use it.

== How the scanner chooses a token

Often more than one pattern matches at the same point in the input. In the
last example, both `number` and `version` match the start of `14.2`. The
scanner decides between them by two rules:

. The pattern that matches the longest text wins. `version` matches all of
  `14.2`, but `number` only `14`.
. When patterns match text of the same length, the pattern defined first in
  the `lex` block wins.

A literal is a pattern too, and the same rules apply to it. This matters for
keywords, which usually match the identifier pattern as well. This program
has a keyword, `if`, and three tokens whose patterns overlap:

* `if` matches the literal and `id`, with the same length. The literal is
  defined first, so `if` is a keyword. If the literal came after `token id`,
  the scanner would read `if` as an `id`, and the program would have no
  keyword at all. Define keywords before the identifier token.
* `iffy` starts with `if`, but `id` matches all four characters, so it is an
  `id`.
* `12` matches `number` and `hex`, with the same length. `number` is defined
  first.
* `12ab` matches `hex` for all four characters, but `number` only for two.
* `abc` matches `id` and `hex`, with the same length. `id` is defined first.

The longest match isn't always the text a token should have. A C comment
runs from `+/*+` to the first `+*/+` after it, but by the first rule,
`+'/*' any* '*/'+` runs from the first `+/*+` to the last `+*/+` in the input,
and takes in all the text between. In `+'/*' any* :>> '*/'+`, the match ends
at the first complete `+*/+`, and a `+*+` on its own inside the comment is
fine. `+--+` can do the same. `+x - y+` removes only text that `y` matches
whole, but `+x -- y+` removes text with a match of `y` anywhere in it, so
`+'/*' ( any* -- '*/' ) '*/'+` reads the same comments as
`+'/*' any* :>> '*/'+`.

* Each comment ends at its first `+*/+`, and the `+*+` inside the second
  one doesn't end it. With plain concatenation in place of `:>>`, the first
  comment would be `+/* one */ b /* two * three */+`.
* Each string ends at its first `+"""+`, and the quotes around `hi` don't
  end it. With `-` in place of `+--+`, or with a plain `+any*+`, the first
  string would run to the last `+"""+` of the line.

`:>` is the operator for an end that is a single character. In
`+'//' any* :> '\n'+`, `+any*+` stops at the first newline, so the token is
one line comment, where plain concatenation would run to the last newline
in the input. The C++ grammar in colm's source tree reads `//` comments this
way. For a longer end, `:>` gives up too soon. `+any*+` stops at the first
`+*+`, so `+'/*' any* :> '*/'+` doesn't match `+/* a * b */+` at all. With
`:>` in place of `:>>` in the last program, the parse fails at the second
comment.

`<:` gives the left side every character it can take. `+'a'* <: 'a' 'b'+`
never matches `aab`, because every `a` goes to `+'a'*+`, and none is left
for the `'a'` after it.

`+x**+` reads the same as `+x*+` when `x` matches single characters:
`+'a'**+` reads `aaa` from `aaab`, and `+[a-z]** 'ing'+` reads `singing`.
When `x` matches longer text, `+**+` drops the ways of matching where a round
of `x` ends though it could go on. `++( [a-z]+ )* 'ing'++` reads `singing`,
but in `++( [a-z]+ )** 'ing'++`, a round that has started takes every letter,
`ing` included, so the pattern matches only the text `ing`. In colm, use
`+*+`. No program in colm's source tree uses `+**+`.

None of these operators can make a match longer. Each only takes away ways
of matching that plain concatenation, `-` or `+*+` would allow.

Ignore patterns take part in the choice by the two rules too, but right
after the parser takes a token they go first. Before each match up to the
next token, the scanner tries the ignore patterns of that token's `lex` block
on their own.
If one of them matches, the scanner skips the text it matches, even when a
token matches more text or is defined first. Only when none of them matches
does the scanner choose by the two rules. So in a single `lex` block, the
two rules decide between an ignore pattern and a token only before the first
token of a parse, and after a token marked `-ni`, which <<regions>> explains.

With a `+#+` token and an ignore pattern for `+#+` followed by letters,
`+#abc+` is ignored and `+#+` alone is a token.

`if`, though `id` matches it too. When no pattern matches at all, the parse
fails as well.

[[regions]]
== Lexical regions

Each `lex` block is a lexical region. A program can have several. When the
parser asks for a token, the scanner uses only the regions that hold the
tokens the parser can take at that point. The patterns of the other regions
play no part, except the ignore patterns of the region of the last token
the parser took, which the scanner tries first, as described below. This
way, different parts of the input can be scanned in different ways.

A token or literal defined outside a `lex` block is in a region of its own.

After the `=`, the parser can take only a `value`, so the scanner reads it
with the second region's patterns. There, only `value` and `nl` can match,
so `x = y + 1` is a single token, and its second `=` is not the literal.
After the line break, the parser can take a `key`, or the end of the input,
so the scanner goes back to the first region.

The second region is what makes this work. In a single `lex` block, `value`
would match each whole line, which is longer than any `key`, so the scanner
would read `name = Ada Lovelace` as one `value`, and the parse would fail at
its start.

The value doesn't start with the space that follows the `=`. After the
parser takes a token, the scanner skips what that token's region ignores,
whatever region the next token is in, and only then reads the next token.
The `=` is in the first region, which ignores spaces, so the space after it
is skipped before the value is read, though the value is in the second
region. To keep this text, put `-ni` after the token's pattern, or after a
literal. Then the text after the token is read with the next token, in the
next token's region, and only that region's ignores apply. The last example
of this chapter uses `-ni`.

So when the parser asks for a token, the scanner tries the patterns in this
order:

. The ignore patterns of the region of the last token the parser took, on
  their own. This step is left out before the first token of a parse, after
  a token marked `-ni`, and after a token from a region with no ignore
  patterns. Each time one of them matches, the scanner skips the text and
  starts this step again.
. When none of them matches, the patterns of the region that holds the
  tokens the parser can take, by the two rules. That region's ignore
  patterns take part in this choice. When one of them wins, the scanner
  skips the text and goes back to the first step.

In the settings example, the line break is in the second region, which has
no ignore patterns, so nothing is skipped after it. The spaces before `born`
are read by the second step, in the first region, where only its ignore
pattern matches them.

A token with an action, which the next section introduces, can give the
parser a different token, or none. The skip follows the token the parser
gets, the one the action pushes, not the one its pattern matched. When the
action drops its token, the skip is still that of the last token the parser
took, if there is one.

Sometimes the parser can take tokens from more than one region. The scanner
then tries those regions in turn. When no pattern in one region matches the
input, it tries the next. Which region comes first depends on the grammar. If
the token from the first region leads to a parse error later, the parser can
go back and read the same text again in the next region.

[[token-actions]]
== Token actions

A token can have an action: a block of code after its pattern, which runs each
time the scanner matches the token. With an action, the token is not passed to
the parser automatically. The action decides what the parser gets. This lets a
program decide what a token is when the input is read, which a pattern alone
can't do.

When the action starts, the matched text is still in the input. In the action:

* `match_text` is the matched text, and `match_length` its length.
* `+input->pull( N )+` takes `N` characters off the input and returns them as a
  string. A pull of more characters than the input has stops the program, as
  xref:8_04_error_handling.adoc#run-time-errors[the error handling chapter]
  says. The text a pull can take ends where the input ends, where the text
  sent to the parser so far ends, or at a token or tree pushed back onto the
  input, with `push` or `push_ignore`.
* `make_token( typeid<T>, Text )` makes a token of type `T`, with `Text` as its
  text. `T` doesn't have to be the token that matched.
* `+input->push( Token )+` puts a token back at the front of the input. The
  parser gets it next.
* [[push-ignore]]`+input->push_ignore( Tree )+` puts a token or tree back at
  the front of the input as ignored text. The parser doesn't get it as a
  token, but the tree keeps it, and printing the tree prints it. Like the
  ignored text the scanner reads, it belongs to the token before it, or to the
  first token at the start of the input, as
  xref:3_03_match.adoc#changing[Changing a tree] explains. It takes a token,
  such as one `make_token` makes, or a tree, such as one a parse makes, but
  not a string.

An action that pulls the text and pushes nothing drops the token, so the
parser never sees it. An action has to pull the matched text, though: if it
doesn't, the scanner matches the same text again, and runs the action again,
without end.

Each push puts its token or tree at the front of the input, ahead of what was
pushed before it, so when an action pushes more than one, the last one pushed
is read first.

An action can declare variables of its own. To use a variable declared at
the top of the program, the variable has to be declared with `global`. A
token with an empty pattern, `//`, never matches any input, so the scanner
never makes one. Code has to make it with `make_token`, as the action in the
next example does.

The action of `here_name` stores the name in the global `HereEnd`. It then

Inside a here-document, the parser can take a `here_line` or a `here_end`, so
the scanner uses the second region. `here_end` has an empty pattern, so the
scanner reads every line as a `here_line`. The action of `here_line` compares
the line with the stored name. If they are the same, it pushes the line as a
`here_end`. Otherwise it pushes it as a `here_line`.

`-ni` after the pattern of `nl` keeps the spaces at the start of the first
line of each document. Without it, the scanner would skip them after the `nl`,
since the first region ignores spaces, and the first line would be printed as
`Dear reader,`.
