[[parsing]]
= Grammars and parsing

The scanner, the subject of xref:3_01_lex.adoc#lexing[the lexing chapter],
breaks the input into tokens. The parser builds a tree from the tokens,
following a grammar. This chapter covers the grammar, written with `def`, and
the `parse` statement, which runs the parser. It then explains how the parser
chooses when the grammar allows more than one tree, and the ways a program can
steer that choice: precedence, `reject`, `commit` and `redef`.

== Grammars

A grammar is made of `def` statements. Each defines a type, whose values are
trees. `def` is followed by the type's name, and then by one or more
productions, separated by `|`. A production is a list of elements in square
brackets. An element is a token's name, a literal in its backtick form, or
the name of a def, including the def being defined:

[source,colm]
----
def term
	[id `* term]
|	[id]
----

A `term` is an `id`, a `+*+` and another `term`, or else a single `id`. `+[]+`
is an empty production, with no elements. It lets a def match no tokens at
all.

An element can be followed by an operator:

* `x?` is an optional `x`.
* `+x*+` is zero or more ``x``s.
* `x+` is one or more ``x``s.

Colm makes a def for each of these. `x?` is `+[x] | []+`, `+x*+` is
`+[x x*] | []+`, and `x+` is `++[x x+] | [x]++`. They are right-recursive.
`+x<*+` and `pass:c[x<+]` match the same as `+x*+` and `x+`, but are
left-recursive: `+[x<* x] | []+` and `++[x<+ x] | [x]++`.

Elements can be grouped in parentheses, with `|` between alternatives, and a
group can take an operator too. `+(`, task)*+` is zero or more commas, each
followed by a `task`. `+(id | number)*+` is zero or more ``id``s and
``number``s, in any order.

An operator right after a literal becomes part of the literal's text.
`+`!?+` is the literal `!?`, not an optional `!`.
With only `+`!+` defined, colm reports an `unknown type` error for it. Close
the literal with a backtick, as in `+`!`?+`, or put it in a def of its own and
make the def optional, as the next example does.

An element can have a label: `Name: type`. For a tree `T`, `T.Name` is the
child that the label names. An element written as a type's name alone, with
no label and no operator, can be read by that name instead, unless the type
is the def's own: `T.type` is the first such child of that type.
xref:3_01_lex.adoc#regions[The lexing chapter's `lex_regions`] prints
`$S.key` this way. A labelled element is read only by its label. To read an
element with an operator, such as `x?` or `+x*+`, or one of the def's own
type, such as the `term` in `+[id `* term]+`, give it a label, as the next
example does with `Mark: urgent?`.

A child that isn't in the production of `T` is nil, so a test such as
`if ( T.declaration )` tells which production `T` has. An optional child,
`x?`, is always there, but has no text when `x` is absent. To test it, label
it and compare its text with `""`.

A name after a production's closing bracket, as in `+[id] :Id+`, names the
production. The `switch` statement, in xref:3_03_match.adoc#patterns[the
chapter on patterns], uses these names.

A def can't have a colm keyword as its name. `list` is one, so `def list` is a
parse error.

== Parsing

`+parse NAME: TYPE[ ... ]+` parses the items in the brackets as a `TYPE`, and
declares the variable `NAME`, which holds the tree. The items are sent to the
parser in order. An item can be `stdin`, a string, a `str` or `int` value, or
a tree, which is sent as its text. `+NAME: TYPE = parse TYPE[ ... ]+` does the
same. An item that is a nil tree, or `nil`, stops the program, as
xref:8_04_error_handling.adoc#run-time-errors[the error handling chapter]
says. The type can be a repetition:

[source,colm]
----
S: str = "cd"
I: int = 42
parse First: items[ "ab " S " " I ]
Second: items = parse items[ First " " stdin ]
parse Words: word*[ "p q r" ]
----

When the input doesn't form a tree of the type, the result is nil, and
`error` holds a message such as `<stdin>:2:4: parse error`.
xref:8_04_error_handling.adoc#error-handling[The error handling chapter] says
where the message points. `parse` ends the input after the last item, so the
whole input must form one tree of the type. A program can also send a parser
its input a piece at a time, and end the input itself, as
xref:3_06_send.adoc#send[the chapter on send] explains.

[[backtracking]]
== Ordered choice and backtracking

The parser builds the tree from the bottom up. It shifts each token: it adds
the token to the elements it holds. When it holds all the elements of a
production, it can reduce them: it makes them the children of a new tree,
whose type is the production's def, and holds that tree in their place.

Colm builds an LALR(1) parser from the grammar. In many grammars, there are
points where the parser could do more than one thing with the next token: it
could shift the token or reduce, or reduce by one production or by another.
Parser generators such as yacc report these points as conflicts. Colm
doesn't. Where the parser could do more than one thing, it tries the
alternatives one at a time, in an order that colm fixes when it builds the
parser. When it meets a parse error, it backs up to the last choice it can
still change, and takes the next alternative there. Backing up undoes
reductions, and puts tokens back into the input. They are scanned again,
maybe in another region, as xref:3_01_lex.adoc#regions[the lexing chapter]
explains.

Some things follow from this:

* Often, the production listed first is tried first. In `parse_order`,
  below, `+a * b;+` fits both productions of `statement`, and the one listed
  first wins. In the grammar of the third point, below, the parser tries `x`
  alone as a `b` before `x y`, and `x y` first if the productions of `b` are
  swapped.
  This is not a rule for every choice, though. Other productions of a def can
  change the order. And without precedence statements, the operators in the
  example of <<precedence,the precedence section>> group to the left,
  whichever of their productions is listed first.
* `x?`, `+x*+`, `x+`, `+x<*+` and `pass:c[x<+]` take as much as they can, and
  give back only what the rest of the production needs. Given `a b c`, where
  `first` and `second` are both an `id`, `+[first* second*]+` puts all three
  in `first`. `+[first* second]+` puts `a b` in `first` and `c` in `second`.
  `+[first? second*]+` puts `a` in `first`, and `b` and `c` in `second`.
* Backing up can change a choice that has already succeeded. In this
  grammar, given `x y y ;`, the parser first takes `x` as a `b`, and then
  fails at the second `y`. It backs up into `b`, and takes `x y` instead:
+
[source,colm]
----
def b
	[`x]
|	[`x `y]

def start
	[b `y `;]
----
+
Given `x y ;`, `b` is `x`. A PEG parser tries a rule's alternatives in the
order they are listed, and keeps the first one that succeeds, so it would
fail on `x y y ;`.
* The parser can look any distance ahead. An error many tokens on can change
  a choice made at the start, as <<reject,the example for `reject`>> shows.

[[precedence]]
== Precedence

`left`, `right` and `nonassoc` give tokens a precedence level. Each is
followed by tokens or literals, separated by commas. A comma right after a
literal becomes part of it, so put a space before the comma, as in
`+left `* , `/+`, or close the literal with a backtick: `+left `*`, `/+`.

Each statement makes a level. The levels of later statements are higher:
their tokens bind tighter. Where the statements are in the file doesn't
matter, only their order.

A production has the level of its last token that has one. When the parser
could shift a token or reduce by a production, and both have a level, it
takes the one with the higher level. When the levels are the same, `left`
reduces, so the operator groups to the left. `right` shifts, so it groups to
the right. `nonassoc` makes it a parse error. The action that loses is
removed from the parser, so backing up after a parse error never tries it.

There is no way to give a production a level of its own. A production for a
minus sign in front of an expression, `+[`- expr]+`, has the level of `-`, so
`+- 1 * 2+` is `+-(1 * 2)+`.

[[reject]]
== Rejecting a reduction

A production can have an action: a block of code after it, which runs when
the parser reduces by the production. In the action, `$r1` is the text of the
production's first element, and `$lhs` the text of the whole production.
xref:3_05_reduction.adoc#reductions[The reductions chapter] covers actions,
`r1` to `rN`, `lhs` and attributes in full.

Actions run on alternatives that the parser later abandons, and run again
when it retries them. What they print stays printed. What they change in
global or context data is undone, as xref:3_04_undo.adoc#context[the context
chapter] explains.

`reject` in an action makes the reduction a parse error. The parser backs up
and tries the next alternative, and the parse fails if there is none. The
rest of the action still runs. Use `reject` only in a production's action.

[[commit]]
== Committing to a parse

To back up, the parser keeps every choice it made. `commit` drops them. It
goes after a production and its name, and before its action. Reducing by a
production with `commit` drops every alternative the parser has kept so far,
in the whole parse, not only inside the production. After that, a parse
error fails the parse instead of backing up past the commit:

[source,colm]
----
def b
	[`x]
|	[`x `y]

def c
	[`y] commit
|	[`z] commit

def start
	[b `y c `z `;]
----

Given `x y y z z ;`, the parser takes `x` as a `b`, the first `y`, and then
the second `y` as a `c`, which commits. The second `z` is a parse error, and
the parse fails. Without the commits, the parser would back up into `b`, take
`x y`, and the parse would succeed.

When a parse fails, the parser first tries every alternative it has kept.
Each statement before the error that can be parsed two ways doubles the
tries. With ten statements such as `+a * b;+` before an error, the grammar of
the next example reduces a statement 2046 times without `commit`, and 10 times
with it. The error is the same either way. Colm's own grammar commits each
definition and statement at the top level of a program.

== Redefining a def

`redef NAME` gives a def new productions, in place of the ones it had. Among
them, `+[...]+` stands for the def's productions as they were, in the same
order. Without `+[...]+`, the old productions are gone. This lets a program
change a grammar from an included file without editing it.

The def must come before the `redef`. Otherwise, colm reports that the redef
is not found. `+[...]+` can only be used in a `redef`. A def can be redefined
more than once, and `+[...]+` then stands for the productions of the last
`redef`.
