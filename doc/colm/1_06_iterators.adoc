[[iterators]]
= Iterators

A `for` loop can visit the trees inside a tree. The trees come from a
grammar, which xref:3_02_parse.adoc#parsing[the parsing chapter] covers, and
the loops here use the patterns of xref:3_03_match.adoc#patterns[the patterns
chapter]. This chapter covers loops over a tree, rewriting a tree from inside
such a loop, colm's built-in iterators, and iterators that a program defines.

== Loops over a tree

`for N: T in S` runs its body once for each tree of type `T` in the tree `S`,
with `N` holding the tree. It visits a tree before the trees inside it, and
goes from left to right. `S` itself is visited first, when it is of type `T`.

`T` must be a tree type, such as a token, a def, `str` or `any`, here and in
a loop over any of the iterators below. Any other type, such as `int`, is a
compile error, `loop variable N must have a tree type`. Loops over a list or
a map are different: their variable can be an `int`, when that is what the
list or the map holds.

The type `T` can be a repetition, such as `+item*+`. A list is its first item
and the rest of the list, which is a list too, down to an empty list at the
end. So the loop visits each list in `S`, and each rest of it.

A loop over a nil tree stops the program: it prints
`fatal: for loop over a nil tree` and exits with status 1. When a C or {cpp}
host runs the program, as in xref:8_01_embedding.adoc#embedding[the embedding
chapter], the host's process ends too. So check a parse's result before
looping over it.

== Rewriting a tree in a loop

Assigning to the loop variable replaces that tree in the tree that the loop
is over. The loop then goes on into the new tree: it visits the trees inside
the replacement, not those inside the tree it replaced, and not the
replacement itself. So if every replacement holds a tree that the body
replaces in the same way, the loop never ends: wrapping each `id` in
parentheses, for example, gives the loop a new `id` to wrap each time.

xref:3_03_match.adoc#changing[Changing a tree], in the patterns chapter,
explains where the ignored text of a replaced tree goes.

Rewrite through a loop over a variable that isn't `global`, such as `Colors`
below. Changes made through the loop variable of a loop over a `global`
variable, or over a field of a struct, are lost: the loop works on a copy.

without end.

== Built-in iterators

A loop can name the iterator that finds its trees, as in
`for N: T in child( S )`. A loop over a tree that names none uses `triter`,
so `for N: T in S` is `for N: T in triter( S )`. Colm has these others:

* `child( S )` visits the children of `S`, from first to last, and
  `rev_child( S )` from last to first. The children of a def's tree are the
  elements of its production.
* `repeat( L )` visits the list `L`, and each rest of it, as a loop over
  `+item*+` does, but only in `L`, not in the lists inside its items. With
  the type of the items as the loop variable's type, it visits the items of
  `L`. `rev_repeat( L )` visits the lists that `repeat( L )` does, from the
  empty one at the end back to `L`.
* `with_ignore( S )` visits the trees that `triter` does, and ignored tokens
  too. An ignore needs a name, as in `+ignore comment /'#' [^\n]*/+`, to be
  the type of a loop variable.

As in a loop with no iterator named, the loop variable's type selects the
trees, and `any` takes every one. Loops over a `list` use other iterators,
such as `rev_list_iter`, which xref:2_02_list_map_struct_alias.adoc#lists[the
lists section] covers.

== User iterators

`+iter Name( Params ) { ... }+` defines an iterator. `for N: T in Name( Args )`
runs the iterator's code. Each `yield V` gives the loop the variable `V`, and
the loop's body runs with `N` holding it. The iterator then goes on after the
`yield`. The loop ends when the iterator's code does.

`yield` takes a variable, which can be qualified, as in `yield T.Name`. It
doesn't take an expression: `yield "x"` is a parse error. The variable must
hold a tree, or be a `ref` to one. A yield of an `int`, a `bool`, a struct, a
list or a map is a compile error, `can only yield a tree`, and so is a yield
of a field that holds one, such as an `int` attribute of a tree.

A function that the iterator calls can yield too, and so can a function that
it calls in turn. The loop gets the value as it gets one from the iterator's
own code. When the loop asks for the next value, the function goes on after
its `yield`, and when it returns, the iterator goes on after the call.

The loop variable's type selects the yields that the body sees. A yield of a
tree of another type is skipped, unless the loop variable's type is `any`.
As in a loop over a tree, the loop variable must have a tree type.

An iterator's parameters are copies, as a function's are. To change the
caller's tree through the loop variable, make the parameter a `ref`.

stay as it was. The space after `+((a))+` belonged to its last `)`, so it
went when `+((a))+` was replaced.

Some rules for user iterators:

* Don't use `exit` in an iterator, or in a function that it calls. A
  `return` in an iterator is a compile error.
* An iterator can't have the name of a function or another iterator in its
  namespace, or, at the top level, of a built-in one: colm reports it as
  redeclared.
* Let a loop over an iterator run to its end, without `break` or `return`,
  if the iterator yields from inside its own loop over a user iterator, as
  `bottom_up` does, or from a function that it calls.
